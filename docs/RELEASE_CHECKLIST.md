# Revenue Engine Release Checklist

This checklist separates local verification from external/production gates. Passing unit tests does not imply that a mail provider, webhook, DNS, payment dashboard, or hosted server works end to end.

## Local checks (must all pass in the target Codespace)

- [ ] `python -m compileall -q app scripts tests`
- [ ] `python -m unittest discover -s tests -v` (include Flask route tests; no skip if requirements are installed)
- [ ] `python -m scripts.preflight`
- [ ] `python -m scripts.preflight --online` (read-only Brevo account and sender checks)
- [ ] `python -m scripts.run_campaign --dry-run --limit 1 --provider brevo` makes no external provider call and does not mutate outreach or lead state.
- [ ] `git status --short` contains no `.env`, local database, archive, generated bytecode, or secrets.
- [ ] Re-check the current landing page and service links in a browser.

## Email gates

- [ ] Confirm the current `hello@sanchit-agarwal.me` sender remains active in Brevo.
- [ ] Confirm the actual live runtime's outbound IP is accepted by Brevo; Codespaces outbound IP is not stable.
- [ ] Configure the Brevo event webhook for the deployed HTTPS endpoint and the authentication method supported by the selected Brevo webhook type. If shared-token headers aren't available, use a trusted proxy with verified source-IP restrictions; do not expose an unauthenticated endpoint.
- [ ] Verify forwarding to the user's Gmail with an actual inbound test.
- [ ] Create an explicitly approved, controlled test-recipient outreach row. Never use a prospect as the initial delivery test.
- [ ] Run a single live email to the controlled mailbox only after the above pass; confirm inbox receipt, provider message ID, `SENT` and then event-driven `DELIVERED`.
- [ ] Verify hard-bounce/complaint/unsubscribe events create suppression rows and cannot be re-prepared.
- [ ] Do not resend an ambiguous timeout. Create a transport retry only after the provider's prior acceptance/non-delivery is independently established.

## Payment gates

- [ ] Configure Razorpay test-mode webhook at the deployed HTTPS `/webhooks/razorpay` endpoint with the dedicated webhook secret.
- [ ] Register a test order-to-lead mapping before checkout or include `notes.revenue_engine_lead_id` in the order.
- [ ] Test signature rejection, duplicate event idempotency, valid capture, amount/currency mapping, and manual reconciliation of unmatched captures.
- [ ] Only a provider-verified captured payment can advance a lead to `PAID`.

## Deployment gates

- [ ] Configure production secrets in host secret management, not in Git.
- [ ] Set `ENVIRONMENT=production` and a strong `FLASK_SECRET_KEY`.
- [ ] Deploy `wsgi:app` using a production WSGI server behind HTTPS.
- [ ] Ensure the SQLite path is persistent and backed up, or migrate to a managed database before multiple instances/workers are used.
- [ ] Confirm webhooks reach the live host, routes return expected responses, and health check `/healthz` succeeds.
- [ ] Confirm log retention, rollback steps, DNS/email authentication, privacy notice/consent and unsubscribe operation.

## Known limitations of this release candidate

- Brevo is the configured primary provider; SendGrid is retained as an optional delivery client but its prior account reported `Maximum credits exceeded` and must not be selected until entitlement is restored.
- Reply ingestion is a deliberate manual operator command; a mailbox API/polling integration is not implemented.
- The source distribution cannot contain live credentials, provider dashboard configuration, DNS state, production hosting, or proof of receipt in an inbox.
- Six Flask route/form tests are skipped in the isolated build environment if Flask isn't installed. They should execute in the actual Codespace after `pip install -r requirements.txt`.
- Before production, review legal and provider requirements for prospecting in each target market and ensure suppression/consent handling is appropriate.
